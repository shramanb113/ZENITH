# ZENITH Roadmap: From Credibility Fixes to a Fundable P1

This document turns the strategic assessment (an Opus-model review of commit `cf0e7c6`, grounded in the actual code and in competitor research current as of September 2026) into a concrete, sequenced execution plan. It exists so that "we should fix the docs" and "we should add filtering" turn into tracked work with acceptance criteria, not just intentions.

Read this alongside `DECISIONS.md` (why things are built the way they are) and `bench/BENCHMARK.md` (the numbers). This document is about what happens next, and in what order, and why that order.

### P0-1 and P0-2 — what actually changed

- `internal/config.Config.MaxResults` was dead (declared, defaulted to 10, never read). It's now the real internal RRF candidate cap (default 1000), wired into all three ranker-construction sites (`pkg/zenith/zenith.go`, `cmd/server/main.go`, `cmd/zenith/engine.go`). `Limit(n)` in the library, `SearchRequest.limit/offset` in gRPC (new proto fields, `internal/server.paginate`), and the CLI's `--max` now all have real candidates to slice from instead of hitting a hardcoded cap of 10 before any of that logic runs.
- `WithMemoryLimit(limitBytes int64)` is implemented in `pkg/zenith/options.go`, using an ~11 KB/doc estimate derived from the measured heap delta in `bench/BENCHMARK.md` (1,127 MB / 100,000 docs). It's approximate accounting by design — documented as such — and exempts overwrites of existing IDs from counting as growth. `Add`/`AddBatch` return `ErrIndexFull` (already declared, now actually reachable) once the projected total would exceed the limit.
- `CLAUDE.md` and `README.md` now describe `internal/localembedder` (the real in-process ONNX embedder) instead of the deleted `nerve/` Python sidecar, and the README's gRPC method list matches `document.proto` exactly (`IndexDocuments`, `Search`, `IndexPDF`, `GetDocument`, `DeleteDocument`).
- Regression tests added: `TestSearch_LimitAboveTen` (`pkg/zenith/zenith_test.go`), three `WithMemoryLimit` tests (`pkg/zenith/options_test.go`), six `paginate` tests (`internal/server/pagination_test.go`).

### P0-3 — CI

Added `.github/workflows/ci.yml`: a matrix over `{ubuntu-latest, macos-latest, windows-latest} × {CGO_ENABLED=0, CGO_ENABLED=1}`, running `go build ./...`, `go vet ./...`, and `go test -race ./...` (race detector requires CGo, so the CGo-off leg skips `-race` and runs a plain `go test`). README badge added. This is the direct mitigation for risk #9 (bus-factor / single-maintainer discount) and risk #10 (credibility gaps) below — an accelerator, or any serious adopter, checks for this before reading anything else.

### P0-4 and P0-5 — what was built, and a deliberate deviation from this document's earlier plan

An earlier revision of this section said to hold both back and ship them together with the segment migration, to avoid a second format bump (risk #5). They were built now instead, because both fix correctness problems that hurt today (silently mixing vector spaces after an embedder change; crash recovery that re-runs ONNX inference for every WAL record) and the codebase's established precedent for a version bump is a hard, explicit `ErrIncompatibleVersion` rather than silent corruption. **The cost is real:** the snapshot is now v5 (unreleased, so no shipped v4 users are stranded by it), and the segment migration (P1-4) will be a further bump. The mitigation for that is P1-1: `zenith migrate` and a published compatibility policy must land *with* the segment format, not after. **Update:** that is exactly what shipped — format v6 (manifest + segments) arrived together with `zenith migrate`, [FORMAT.md](./FORMAT.md) and golden-file tests (see P1-1 and P1-4), so the v5 snapshot described here is now a migration source (`zenith migrate` reads it), not a lasting format.

What changed:

- **P0-5** — the snapshot header now stores the embedder name and vector dimension before the gob body; `Load` fails fast with `ErrEmbedderMismatch` (surfaced as `zenith.ErrEmbedderMismatch`) without decoding the body. Embedders identify themselves through an optional `embedding.Named` interface, so custom `WithEmbedder` types are not a breaking change; an embedder that doesn't implement it is recorded as `unknown` and never mismatch-checked.
- **P0-4** — `Add`/`AddBatch` embed once and reuse the vector for both the WAL record and indexing; replay calls `AddWithVectorAttrs` and never touches the embedder for the document vector. A WAL past 64MB triggers a synchronous checkpoint even when `WithCheckpointInterval` was never set. Per-token word vectors are still warmed on replay; they are deduplicated by vocabulary, so that cost is bounded by unique terms, not documents. Old raw-text WAL values still decode (legacy fallback).

## P1: table stakes (1–3 months)

Ordered by dependency, not by the report's original numbering — filtering and the format migration gate several other items.

1. **`zenith migrate` tool + published compatibility policy.** **DONE.** `zenith migrate` (and `zenith.Migrate` from Go) converts an older index in place: it copies the original aside as `<file>.v<N>.bak`, writes the new index beside it, swaps it in atomically, then re-opens and checksums the result — no embedding model needed, vectors are copied. Until migrated, an older-format file is *refused with a typed error* (`*LegacyFormatError`, matches `ErrIncompatibleVersion`) and `Save` will not overwrite it; an early version of the CLI treated any load error as "no index yet" and would have replaced a user's index with an empty one, which is why that path is now covered by tests. The policy is [FORMAT.md](./FORMAT.md). It is enforced by golden files in `internal/index/testdata/`: a **real format-5 index written by the previous release's own library**, with the search results that release returned, is migrated in CI and must answer all 11 recorded queries (typo, semantic, filtered) identically. **Caveats:** only formats 4 and 5 migrate (3 and older: re-index); the policy is a pre-1.0 commitment to migrate from the *immediately preceding* format, with the every-1.x-opens-in-every-later-1.x promise starting at 1.0. **[FMT]**
2. **Metadata and filtering** — **DONE at the library level.** `AddWithAttrs` / `AddBatchWithAttrs`, `WithFilter(Eq | In | Range | Exists | And | Or | Not)`, applied to the lexical *and* vector candidate sets before rank fusion (so `Limit(1)` returns the best *matching* document, not a filtered view of the global top), persisted in the snapshot and the WAL. **Not yet done:** roaring-bitmap postings for high-selectivity filters (today it is a per-candidate predicate, O(candidates)), gRPC/HTTP/CLI surface for attributes, and `Explain` + `WithFilter` (currently rejected with `ErrInvalidOption`).
3. **Lexical candidate pass rebuild** — **DONE (WAND/MaxScore deliberately not built).** Measured on real MS MARCO (107,399 passages, lexical mode, index memory-mapped): the query path was spending its time on candidates that could never rank — **73,543 lexical candidates per query, only 4,319 (6%) with any BM25 hit** — and fuzzy matching alone reached 70,560 of them (a fixed edit distance of 2 makes a 2–3 letter word match hundreds of unrelated terms), versus ~6,000 from prefix expansion — the earlier plan had targeted the prefixes. Changes: (a) **length-scaled fuzzy distance** (`Config.FuzzyByLength`, default on: ≤3 letters exact, 4–5 letters one edit, longer `FuzzyMaxDist`); (b) **capped prefix expansion** (`Config.PrefixFragmentCap`: a prefix shared by more than max(2,000, 2% of docs) documents stops generating candidates; the full-token fragment never does); (c) rank fusion resolves document names lazily and, with no vector list, selects the top-N without sorting every candidate (exact — tested against the full sort under heavy ties); (d) BM25 is computed once per query instead of twice; (e) TF-IDF maintenance dropped; plus the earlier Levenshtein-automaton fuzzy search. **Result on the 300-query sample: p50 201 ms → 43 ms (4.7×), p95 300 → 104 ms, Recall@10 unchanged at 0.830, typo-query Recall@10 0.550 → 0.553** (one edit in the longest 6+ letter word of each query; the ablation is in the config comment). Full 6,980-query run after all changes: **p50 8.6 ms (from 249 ms in-memory before any change, 29x), p95 21.7 ms (from 960), p99 29.9 ms (from 1,526); Recall@10 0.8468 (0.8471 before: two queries of 6,980 differ)**, typo-query Recall@10 0.5876 over 6,213 typo'd queries. The 43 ms sample figure above predates (c), which delivered the rest. A 2×2 ablation showed length-scaled fuzziness is the 4× and the prefix cap the extra ~20%; the prefix cap alone was ~nothing, which is how the real cost was found. **CI gate:** `TestLexicalLatencyGate` (recall floors, a machine-independent bound on candidates per query, a loose p50 ceiling) on a deterministic synthetic corpus; verified to fail on the old behaviour (20.8k vs 9.2k candidates/query, p50 36 vs 13 ms). **Not done, and the profile says why:** WAND/MaxScore. In the final-state profile BM25 scoring is 9% of query time (candidate generation ≈ 39% — posting decode and score-map inserts for prefix/phonetic/fuzzy fragments; rank fusion ≈ 22%; the FST fuzzy walk ≈ 13%), so pruning it could not move the p50 much; the hybrid path does not get the top-N shortcut (its vector list needs exact keyword ranks), and hybrid p50 is still far from the risk table's sub-20 ms target (see item 5).
4. **Memory-mapped immutable segments + tombstones** — **DONE.** The index is a stack of immutable, memory-mapped segment files (`internal/segment`) plus a small in-memory delta; `zenith.db` is a manifest that names the segments ([FORMAT.md](./FORMAT.md)). Search reads the delta and every segment through one set of iterators, and is **result-identical to a single in-memory index** — enforced by a differential test that drives both through the same adds, replaces and deletes across flush, compaction and reload (bit-for-bit for lexical, vector and attribute-filtered results including word vectors; the approximate ANN graph is checked separately against exact search across flush, compaction and reload). Saving flushes only the delta as a new segment (cost ∝ the delta, not the index); deletes of segment documents are dead-row bitsets persisted in the next segment; `Compact()` merges segments without holding the engine lock (streaming k-way merge; the lock is held only to snapshot and to swap) and runs automatically past 8 segments or a high dead ratio. **Memory: 16.5 → 7.5 KB/doc on the Go heap** for the in-memory representation (by no longer storing per-document derived data — the BK-tree, TF-IDF statistics and per-document fragment lists are gone or recomputed on demand) and, once mapped, the postings, vectors and documents live in the OS page cache instead: the 107k-passage MS MARCO index with real 384-dim vectors is **155 MB on disk (~1.45 KB/doc)** and opens in milliseconds. **Measured checkpoint pause** (100k-doc base, real-size 384-dim vectors, ANN active): the engine write lock is held for the flush — **96 ms for a 1k-doc delta, 0.56 s for 10k, 1.7 s for 30k** (about 56 µs/doc plus ~40 ms of fsyncs). Cost is now proportional to the delta, no longer to the index, but searches still stall for it; a flush that never blocks searches (a frozen-memtable design) is not built. At an estimated ~2 KB per WAL record the default 64 MB WAL threshold is roughly 30k documents, i.e. a size-triggered checkpoint pauses searches for ~1.7 s. Compaction is lock-free except the swap: merging 141k docs took 6.3 s with a longest concurrent search stall of ~350 ms. **Known costs and limits:** attributes for live documents and each segment's dead-row bitset stay on the heap; the ANN graph is not persisted (rebuilt on open, re-pointed at the new mapping after each flush/compaction); segments assume a little-endian host (refused otherwise); Windows cannot delete or replace a mapped file, so layers are unmapped before their files go and `Engine.Close` is required before removing an index directory; the Unix mmap path has been compiled and vetted for linux/darwin but its first *execution* is in CI. **[FMT]**
5. **ANN index (HNSW, pure Go, filter-aware)** — **DONE, not persisted.** `internal/ann` is a pure-Go HNSW over the existing float16 vectors (graph only; no second copy of the vectors). `vectorPass` uses it above `WithANNThreshold` (default 20,000 docs) and scans exactly below that. Filters run inside graph traversal; below 10% selectivity it falls back to an exact scan over the allowed documents. Measured: recall@10 0.967 vs brute force (6k clustered 64-dim vectors, ef=64); top-10 overlap 1.000 with exact hybrid search in the engine test; vector pass at 30k docs (64-dim) **9.2ms exact → 0.62ms ANN**. **Known costs:** the graph is rebuilt from stored vectors on `Open` (not saved to disk — persisting it belongs with the P1-4 segment format), so very large indexes pay build time at startup; ANN hands `annK=150` candidates to rank fusion rather than every positive-scoring document; **recall on real embeddings is now measured**, on 107,399 MS MARCO passages with the real ONNX models: top-10 overlap with the exact scan **0.988** (MiniLM) / **0.982** (gte-small); hybrid Recall@10 **0.954 vs 0.962** exact (0.951 vs 0.962), and p50 **76 → 34 ms** (88 → 35 ms) — so the default costs about one point of Recall@10 for a >2x faster query; whether tuning annK/annEF recovers it has not been tried. The graph is still rebuilt on open (not persisted) and is now re-pointed at the new mapping after each flush/compaction.
6. **Model registry + a better model** — **DONE.** The bundled default is now **`gte-small`** (tied in-domain, +4.7 nDCG points out-of-domain in hybrid, at ~1.7x embedding cost); existing indexes are protected because the index decides its model — they need a one-time `zenith models pull all-MiniLM-L6-v2`, then work as before. `internal/modelspec` lists models by ID (all-MiniLM-L6-v2, gte-small, bge-small-en-v1.5 — all sharing the BERT-uncased vocabulary; multilingual-e5-small needs a SentencePiece tokenizer and is deliberately not listed until one exists). Select with `--model <id>` / `zenith.WithModel(id)`; `zenith models list|pull <id>` installs non-bundled ones (the registry names upstream files and does not pin checksums, so `pull` records the SHA-256 of what it fetched). An explicitly requested model that cannot load is an *error*, never a silent downgrade. **The index decides its model:** an index records `onnx:<id>` in its header, refuses to open with another (`ErrEmbedderMismatch`, with the exact way forward in the CLI), and the CLI follows the recorded model automatically when `--model` is not given — so changing the bundled default never strands an existing index. Measured, dense-only (no lexical signal, so the numbers isolate the model; MS MARCO = 2,000 dev queries over a 20k-doc slice, SciFact = full BEIR test split): all-MiniLM-L6-v2 nDCG@10 **0.946** / SciFact **0.652** (23 MB, 2m19s to embed 20k docs); bge-small-en-v1.5 **0.961** / **0.699** (34 MB, 4m30s; the query instruction prefix helps MS MARCO and slightly hurts SciFact); **gte-small 0.965 / 0.714** (34 MB, 3m52s). Full hybrid pipeline (lexical + dense + RRF): **out-of-domain SciFact** (300 queries, 5,183 docs): nDCG@10 lexical-only 0.689, +all-MiniLM-L6-v2 0.691, +bge-small 0.727, **+gte-small 0.738** (Recall@10 0.820 / 0.823 / 0.848 / **0.866**); **in-domain MS MARCO** (107,399 docs, 1,000 queries, exact vector scan): Recall@10 **0.962 for both** MiniLM and gte-small. So the previous default added almost nothing to BM25 on out-of-domain text, while gte-small adds +5 nDCG points; on in-domain text they tie. Cost of gte-small: ~1.7x embedding time (107k passages 21m41s vs 12m45s) and an 11 MB larger binary. *Caveat: the MS MARCO slice is in-domain for models trained on it and flatters them; SciFact is the more representative number for arbitrary user documents.*
7. **Honest, reproducible benchmarks** — **PARTIAL (harness only; no new numbers published).** Done: the `bench` module was not building at all (missing `golang.org/x/text` in its `go.sum`; fixed), and `go run ./cmd/benchmark --queryset=typo|codemixed --seed=N` now derives seeded, deterministic query sets from the MS MARCO queries (`bench/internal/queryset`, unit-tested), graded against the same qrels. `typo` applies one realistic edit (delete/repeat/nearby-key/transposition, never the first letter) per eligible word. `codemixed` is a **synthetic noise proxy** (romanised-Hindi function words interleaved with English content words) — it cannot test romanised spelling variation or Devanagari, so replace it with human-authored code-mixed data before making any Hinglish quality claim. **Also done since:** gated real-corpus tests — lexical latency + recall + typo recall on MS MARCO (`TestMSMARCOLexicalLatency`), real-embedding hybrid + ANN recall (`TestMSMARCOHybrid`), out-of-domain hybrid on BEIR SciFact (`TestSciFactHybrid`), per-model dense comparison (`TestModelComparison`), and a flush/compaction pause measurement (`TestFlushPause`); numbers are in items 3–6. **Not done, and needs your machine/network:** the MS MARCO download (no `.cache` here), Bleve/SQLite runs of the new sets, and competitors that need extra infrastructure (chromem-go, sqlite-vec, LanceDB, Meilisearch, Qdrant), BEIR subsets, and per-signal ablations.

### Monetization guardrails (risk #11) — rules applied while building

The open-core plan only works if the free engine stays trustworthy and the paid layer has somewhere to attach. These are constraints on every change, and where the code already leaves room:

1. **No telemetry, ever, by default.** A local-first search engine that phones home forfeits the funnel top. `zenith doctor --json` exists so a user *chooses* to attach diagnostics to a support request (versions, OS, paths, check outcomes — never index contents or queries); nothing is sent automatically. This is the paid-support on-ramp without a data-collection liability.
2. **No license-gated core features.** Filtering, crash recovery, install tooling, and the embedder-mismatch guard stay in the MIT library. What is left to charge for is operations, not correctness: hosted namespaces, backups/replicas, SLAs, and regional-language deployment support.
3. **Seams a hosted tier needs, already in place:** metadata attributes + pre-fusion filtering are the natural per-tenant isolation key (`Eq("tenant", id)`); the embedder identity header lets a hosted service swap or version models without silently corrupting customer indexes; `WithMemoryLimit` gives a per-tenant resource cap; versioned formats fail loudly instead of corrupting.
4. **Exit stays cheap.** Data lives in one directory; `zenith uninstall` keeps it by default and only deletes on explicit `--purge`. Lock-in through data hostage would poison an open-core funnel.
5. **What is still missing for monetization, deliberately not built yet (P2/P3 are gated on real users):** auth/quotas/metrics on the server, an export/backup command that a hosted tier could import, and tenant-aware limits. **Flag:** the repo had no `LICENSE` file although the README says MIT — without one, the open-core story is legally ambiguous to any adopter. A `LICENSE` file has been added to match the README; the copyright holder line is the maintainer's to confirm.
