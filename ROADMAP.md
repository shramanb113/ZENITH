# ZENITH Roadmap: From Credibility Fixes to a Fundable P1

This document turns the strategic assessment (an Opus-model review of commit `cf0e7c6`, grounded in the actual code and in competitor research current as of September 2026) into a concrete, sequenced execution plan. It exists so that "we should fix the docs" and "we should add filtering" turn into tracked work with acceptance criteria, not just intentions.

Read this alongside `DECISIONS.md` (why things are built the way they are) and `bench/BENCHMARK.md` (the numbers). This document is about what happens next, and in what order, and why that order.

- **DONE** — implemented and verified in this repo, not just planned.

### P0-1 and P0-2 — what actually changed

- `internal/config.Config.MaxResults` was dead (declared, defaulted to 10, never read). It's now the real internal RRF candidate cap (default 1000), wired into all three ranker-construction sites (`pkg/zenith/zenith.go`, `cmd/server/main.go`, `cmd/zenith/engine.go`). `Limit(n)` in the library, `SearchRequest.limit/offset` in gRPC (new proto fields, `internal/server.paginate`), and the CLI's `--max` now all have real candidates to slice from instead of hitting a hardcoded cap of 10 before any of that logic runs.
- `WithMemoryLimit(limitBytes int64)` is implemented in `pkg/zenith/options.go`, using an ~11 KB/doc estimate derived from the measured heap delta in `bench/BENCHMARK.md` (1,127 MB / 100,000 docs). It's approximate accounting by design — documented as such — and exempts overwrites of existing IDs from counting as growth. `Add`/`AddBatch` return `ErrIndexFull` (already declared, now actually reachable) once the projected total would exceed the limit.
- `CLAUDE.md` and `README.md` now describe `internal/localembedder` (the real in-process ONNX embedder) instead of the deleted `nerve/` Python sidecar, and the README's gRPC method list matches `document.proto` exactly (`IndexDocuments`, `Search`, `IndexPDF`, `GetDocument`, `DeleteDocument`).
- Regression tests added: `TestSearch_LimitAboveTen` (`pkg/zenith/zenith_test.go`), three `WithMemoryLimit` tests (`pkg/zenith/options_test.go`), six `paginate` tests (`internal/server/pagination_test.go`).

### P0-3 — CI

Added `.github/workflows/ci.yml`: a matrix over `{ubuntu-latest, macos-latest, windows-latest} × {CGO_ENABLED=0, CGO_ENABLED=1}`, running `go build ./...`, `go vet ./...`, and `go test -race ./...` (race detector requires CGo, so the CGo-off leg skips `-race` and runs a plain `go test`). README badge added. This is the direct mitigation for risk #9 (bus-factor / single-maintainer discount) and risk #10 (credibility gaps) below — an accelerator, or any serious adopter, checks for this before reading anything else.

### P0-4 and P0-5 — what was built, and a deliberate deviation from this document's earlier plan

An earlier revision of this section said to hold both back and ship them together with the segment migration, to avoid a second format bump (risk #5). They were built now instead, because both fix correctness problems that hurt today (silently mixing vector spaces after an embedder change; crash recovery that re-runs ONNX inference for every WAL record) and the codebase's established precedent for a version bump is a hard, explicit `ErrIncompatibleVersion` rather than silent corruption. **The cost is real:** the snapshot is now v5 (unreleased, so no shipped v4 users are stranded by it), and the segment migration (P1-4) will be a further bump. The mitigation for that is P1-1: `zenith migrate` and a published compatibility policy must land *with* the segment format, not after. **Update:** that is exactly what shipped — format v6 (manifest + segments) arrived together with `zenith migrate`, [FORMAT.md](./FORMAT.md) and golden-file tests (see P1-1 and P1-4), so the v5 snapshot described here is now a migration source (`zenith migrate` reads it), not a lasting format.

What changed:

- **P0-5** — the snapshot header now stores the embedder name and vector dimension before the gob body; `Load` fails fast with `ErrEmbedderMismatch` (surfaced as `zenith.ErrEmbedderMismatch`) without decoding the body. Embedders identify themselves through an optional `embedding.Named` interface, so custom `WithEmbedder` types are not a breaking change; an embedder that doesn't implement it is recorded as `unknown` and never mismatch-checked.
- **P0-4** — `Add`/`AddBatch` embed once and reuse the vector for both the WAL record and indexing; replay calls `AddWithVectorAttrs` and never touches the embedder for the document vector. A WAL past 64MB triggers a checkpoint even when `WithCheckpointInterval` was never set (a checkpoint no longer blocks searches — see P1-4). Per-token word vectors are still warmed on replay; they are deduplicated by vocabulary, so that cost is bounded by unique terms, not documents. Old raw-text WAL values still decode (legacy fallback).

## P1: table stakes (1–3 months)

Ordered by dependency, not by the report's original numbering — filtering and the format migration gate several other items.

1. **`zenith migrate` tool + published compatibility policy.** **DONE.** `zenith migrate` (and `zenith.Migrate` from Go) converts an older index in place: it copies the original aside as `<file>.v<N>.bak`, writes the new index beside it, swaps it in atomically, then re-opens and checksums the result — no embedding model needed, vectors are copied. Until migrated, an older-format file is *refused with a typed error* (`*LegacyFormatError`, matches `ErrIncompatibleVersion`) and `Save` will not overwrite it; an early version of the CLI treated any load error as "no index yet" and would have replaced a user's index with an empty one, which is why that path is now covered by tests. The policy is [FORMAT.md](./FORMAT.md). It is enforced by golden files in `internal/index/testdata/`: a **real format-5 index written by the previous release's own library**, with the search results that release returned, is migrated in CI and must answer all 11 recorded queries (typo, semantic, filtered) identically. **Caveats:** only formats 4 and 5 migrate (3 and older: re-index); the policy is a pre-1.0 commitment to migrate from the *immediately preceding* format, with the every-1.x-opens-in-every-later-1.x promise starting at 1.0. **[FMT]**
2. **Metadata and filtering** — **DONE (library, gRPC, HTTP, CLI; compressed postings and README docs deferred — item H).** `AddWithAttrs` / `AddBatchWithAttrs`, `WithFilter(Eq | In | Range | Exists | And | Or | Not)`, applied to the lexical *and* vector candidate sets before rank fusion (so `Limit(1)` returns the best *matching* document, not a filtered view of the global top), persisted in the snapshot and the WAL. A filter is also *data* (`index.FilterSpec`, JSON ops `eq`, `in`, `range`, `exists`, `and`, `or`, `not`, `none`; depth ≤ 16, ≤ 512 nodes), so the same filter works everywhere: `zenith.FilterFromJSON`, gRPC (`SearchRequest.filter`, `IndexRequest.attrs`), the HTTP sidecar's JSON body, and the CLI (`zenith index --attr k=v`, `zenith search --where k=v` / `--filter '<json>'`). `Explain` now combines with `WithFilter`. A per-field value → ordinal index (`internal/index/attrindex.go`) answers selective filters (estimate ≤ max(2,000, docs/50)) by scoring only the matching documents in the vector pass; `Not` falls back to a scan, and the index path is property-tested to equal the scan path. **Not done:** the postings are sorted ordinal slices, not roaring-style compressed bitmaps; the filter JSON, CLI flags and gRPC/HTTP surface are not yet in the README.
3. **Lexical candidate pass rebuild** — **DONE (WAND/MaxScore deliberately not built).** Measured on real MS MARCO (107,399 passages, lexical mode, index memory-mapped): the query path was spending its time on candidates that could never rank — **73,543 lexical candidates per query, only 4,319 (6%) with any BM25 hit** — and fuzzy matching alone reached 70,560 of them (a fixed edit distance of 2 makes a 2–3 letter word match hundreds of unrelated terms), versus ~6,000 from prefix expansion — the earlier plan had targeted the prefixes. Changes: (a) **length-scaled fuzzy distance** (`Config.FuzzyByLength`, default on: ≤3 letters exact, 4–5 letters one edit, longer `FuzzyMaxDist`); (b) **capped prefix expansion** (`Config.PrefixFragmentCap`: a prefix shared by more than max(2,000, 2% of docs) documents stops generating candidates; the full-token fragment never does); (c) rank fusion resolves document names lazily and, with no vector list, selects the top-N without sorting every candidate (exact — tested against the full sort under heavy ties); (d) BM25 is computed once per query instead of twice; (e) TF-IDF maintenance dropped; plus the earlier Levenshtein-automaton fuzzy search. **Result on the 300-query sample: p50 201 ms → 43 ms (4.7×), p95 300 → 104 ms, Recall@10 unchanged at 0.830, typo-query Recall@10 0.550 → 0.553** (one edit in the longest 6+ letter word of each query; the ablation is in the config comment). Full 6,980-query run after all changes: **p50 8.6 ms (from 249 ms in-memory before any change, 29x), p95 21.7 ms (from 960), p99 29.9 ms (from 1,526); Recall@10 0.8468 (0.8471 before: two queries of 6,980 differ)**, typo-query Recall@10 0.5876 over 6,213 typo'd queries. The 43 ms sample figure above predates (c), which delivered the rest. A 2×2 ablation showed length-scaled fuzziness is the 4× and the prefix cap the extra ~20%; the prefix cap alone was ~nothing, which is how the real cost was found. **CI gate:** `TestLexicalLatencyGate` (recall floors, a machine-independent bound on candidates per query, a loose p50 ceiling) on a deterministic synthetic corpus; verified to fail on the old behaviour (20.8k vs 9.2k candidates/query, p50 36 vs 13 ms). **Not done, and the profile says why:** WAND/MaxScore. In the final-state profile BM25 scoring is 9% of query time (candidate generation ≈ 39% — posting decode and score-map inserts for prefix/phonetic/fuzzy fragments; rank fusion ≈ 22%; the FST fuzzy walk ≈ 13%), so pruning it could not move the p50 much; the hybrid path got its own exact shortcut afterwards (`internal/ranking/rrf_hybrid.go`): a profile of the hybrid query showed rank fusion at **73%** of the time (it sorted and mapped all ~73k lexical candidates to fuse them with ~300 vector hits) and embedding only ~3%. A document can only reach the top-N if it is in the vector list or is one of the top-N keyword-only entries, and its keyword rank follows from a binary search against the sorted vector-list documents, so the result is *identical* to the full sort — tested against it on 54 randomized scenarios with heavy ties (`TestRRF_HybridShortcutMatchesFullSort`) and checked by mutation. Engine-only hybrid p50 went **39.6 → 12.5 ms** (ANN, `annK=150`), Recall@10 unchanged; the profile share of `RRFRanker.Score` fell to ~2%. Measured on an unthrottled CPU; see item 5 for the caveat about later, slower runs.
4. **Memory-mapped immutable segments + tombstones** — **DONE.** The index is a stack of immutable, memory-mapped segment files (`internal/segment`) plus a small in-memory delta; `zenith.db` is a manifest that names the segments ([FORMAT.md](./FORMAT.md)). Search reads the delta and every segment through one set of iterators, and is **result-identical to a single in-memory index** — enforced by a differential test that drives both through the same adds, replaces and deletes across flush, compaction and reload (bit-for-bit for lexical, vector and attribute-filtered results including word vectors; the approximate ANN graph is checked separately against exact search across flush, compaction and reload). Saving flushes only the delta as a new segment (cost ∝ the delta, not the index); deletes of segment documents are dead-row bitsets persisted in the next segment; `Compact()` merges segments without holding the engine lock (streaming k-way merge; the lock is held only to snapshot and to swap) and runs automatically past 8 segments or a high dead ratio. **Memory: 16.5 → 7.5 KB/doc on the Go heap** for the in-memory representation (by no longer storing per-document derived data — the BK-tree, TF-IDF statistics and per-document fragment lists are gone or recomputed on demand) and, once mapped, the postings, vectors and documents live in the OS page cache instead: the 107k-passage MS MARCO index with real 384-dim vectors is **155 MB on disk (~1.45 KB/doc)** and opens in milliseconds. **Checkpoints no longer block searches.** A flush freezes the delta in O(1) under the engine lock (the frozen layer stays searchable, read-only, with its own dead set), writes the segment with no engine lock, then swaps it in and commits the manifest; at the package level the WAL is rotated at the same moment, so a checkpoint's slow part (segment write, fsyncs, WAL archive deletion) runs beside queries. Measured on a 100k-doc base with real-size 384-dim vectors and ANN active, with a cheap (~1 ms) probe query running continuously beside the save: saving a 1k / 10k / 30k-doc delta took 0.58 / 1.07 / 2.38 s; probe p50 before → during was 11.7 → 18.0 ms (1k delta, only 12 samples during the save), 13.1 → 13.5 ms (10k) and 16.5 → 16.2 ms (30k). The previous design held the write lock for the whole flush (96 ms / 0.56 s / 1.7 s of stalled searches). **Caveat:** the *maximum* probe latency during the write (150–240 ms) is above the maximum before it (30–60 ms) on these small samples, and the cause is not diagnosed. Compaction is lock-free except the swap: merging 141k docs took 8.0 s with a longest concurrent search stall of 436 ms. A frozen layer whose write fails stays in place and is retried on the next flush; deletions of frozen docs are carried forward. **Known costs and limits:** attributes for live documents and each segment's dead-row bitset stay on the heap; the ANN graph is persisted as the `<db>.ann` sidecar (see item 5) and re-pointed at the new mapping after each flush/compaction; segments assume a little-endian host (refused otherwise); Windows cannot delete or replace a mapped file, so layers are unmapped before their files go and `Engine.Close` is required before removing an index directory; the Unix mmap path is compiled, vetted, **and now executed for real** on WSL Ubuntu ext4 (`internal/segment` + `internal/index`, see Deferred backlog item G). **[FMT]**
5. **ANN index (HNSW, pure Go, filter-aware)** — **DONE, persisted.** `internal/ann` is a pure-Go HNSW over the existing float16 vectors (graph only; no second copy of the vectors). `vectorPass` uses it above `WithANNThreshold` (default 20,000 docs) and scans exactly below that. Filters run inside graph traversal; below 10% selectivity it falls back to an exact scan over the allowed documents. Measured: recall@10 0.967 vs brute force (6k clustered 64-dim vectors, ef=64); top-10 overlap 1.000 with exact hybrid search in the engine test; vector pass at 30k docs (64-dim) **9.2ms exact → 0.62ms ANN**. **Persistence:** the graph is saved beside the manifest as `<db>.ann` (magic `ZANN`, version, HNSW parameters, embedder identity, CRC32C; format in [FORMAT.md](./FORMAT.md)) after every compaction, on `Close`, and in the background after 50,000 graph changes. It is a *hint*, never the source of truth: every node carries the generation tag of the segment its vector lives in and is bound by id and tag at load; documents the file lacks are inserted, nodes for documents that are gone are tombstoned, and a file that is corrupt, built for another embedder, or missing more than half the documents is ignored and the graph is rebuilt from the vectors. Saving copies the graph in small chunks under the read lock, so it does not stop searches; a failed save is harmless (the next open rebuilds). **Open time, measured** (107,399 real gte-small vectors; CPU throttled to ~1.5 GHz at the time, so absolute times are pessimistic): building the graph from the vectors **5 m 26 s**, restoring it from the 8.9 MB sidecar **0.42 s**, and the restored graph answered 300 real queries with **identical top-10 lists to the built one (0 of 300 differ)** (`TestANNSidecarOpenTime`). The graph is re-pointed at the new mapping after each flush/compaction. **Tuning and recall on real embeddings** (107,399 MS MARCO passages, gte-small, 1,000 queries; engine-only sweep, unthrottled): `annK`/`annEF` 150/200 → Recall@10 0.951, p50 12.5 ms; **300/400 (now the default) → 0.957, 14.5 ms**; 600/800 → 0.958, 18.0 ms; 1000/1200 → 0.958, 21.0 ms; 2000/2400 → 0.960, 29.6 ms; 4000/4400 → 0.960, 78.6 ms — 300/400 is the knee (exact scan: 0.962). Final full pipeline run with the fix (`TestMSMARCOHybrid`, **CPU throttled: embedding p50 7.8 ms against 4.2 ms earlier, and the CPU measured at ~1.5 GHz / 52% performance afterwards**): exact scan Recall@10 0.9620, p50 106 ms overlapped; ANN 0.9570, p50 30.6 ms overlapped (39 ms serial, cold cache); ANN-vs-exact top-10 overlap **0.9904**. **Retraction:** the earlier "hybrid p50 76 → 34 ms (88 → 35 ms)" compared a warm-cache ANN run with a cold-cache exact run; it is withdrawn, and the same-condition comparison is 106 ms exact vs 30.6 ms ANN in the throttled run. **Settled, 2026-10-03** (AC power, CPU clock verified via `typeperf` climbing 62→85% off the earlier ~45%-throttled baseline, not sampled during the run itself — see Deferred backlog note below): `TestMSMARCOHybrid` — embedding alone p50 36.81 ms / p95 66.37 / p99 84.68 (gte-small; the earlier 4.2–7.8 ms figures were a smaller/throttled machine state, not a different code path); exact scan Recall@10 0.9620, p50 82.67 ms overlapped (645.73 ms serial cold); **ANN (300/400) Recall@10 0.9570, p50 12.61 ms overlapped / 12.40 ms engine-only warm (14.53 ms serial cold), p95 ~25 ms, p99 ~32–34 ms**, top-10 overlap vs exact 0.9904. `TestHybridEngineLatency` (engine-only, embeddings pre-cached, 3 passes): Recall@10 0.9570, p50 14.56–14.66 ms, p95 28–29 ms, p99 38–39 ms. This confirms the 14.5 ms figure at 300/400 and shows the earlier throttled 26–31 ms runs were a machine artifact, not a code regression — the question is closed, no rerun owed anymore.
6. **Model registry + a better model** — **DONE.** The bundled default is now **`gte-small`** (tied in-domain, +4.7 nDCG points out-of-domain in hybrid, at ~1.7x embedding cost); existing indexes are protected because the index decides its model — they need a one-time `zenith models pull all-MiniLM-L6-v2`, then work as before. `internal/modelspec` lists models by ID (all-MiniLM-L6-v2, gte-small, bge-small-en-v1.5 — all sharing the bert-base-uncased vocabulary; multilingual-e5-small needs a SentencePiece tokenizer and is deliberately not listed until one exists). **Multilingual, 2026-10-03:** `labse` (LaBSE) is now registered — still WordPiece, just cased with its own larger vocab (`Spec.VocabURL`/`Spec.Cased`, fetched by `zenith models pull labse`), 768-dim, opt-in only. Picking the ONNX export mattered: the obvious `Xenova/bert-base-multilingual-cased` repo is a `BertForMaskedLM` export (output `logits` over the vocab, no hidden states) and cannot embed at all — caught by inspecting the ONNX graph's input/output names before wiring it in, not by a failed test. `labse`'s base ONNX export exposes `last_hidden_state` only (no sentence-transformers' final dense+normalize layer), so it was initially CLS-pooled directly here: smoke-tested across five languages (`internal/localembedder/multilingual_test.go`, `ZENITH_MODEL_EVAL=1`), not BEIR-benchmarked — usable cross-lingual signal, not published LaBSE numbers. **Fixed, 2026-10-03** (see the accuracy check below for why): `sentence-transformers/LaBSE`'s own module config was checked directly rather than guessed at — `1_Pooling/config.json` confirms CLS pooling is in fact correct, and the real missing piece is `2_Dense`, a small (2.4 MB) separately-saved trained `Linear(768,768)+Tanh` projection. `Spec.DenseURL` now fetches it via `zenith models pull labse` and `internal/localembedder` applies it after CLS pooling (`internal/localembedder/safetensors.go` parses the file; unit-tested). This reconstructs the real sentence-transformers pipeline instead of approximating it, and it measurably fixed the anisotropy problem for same-language retrieval: `TestMultilingualSmoke`'s correct-passage similarity scores went from a compressed near-threshold band to a properly spread **0.32–0.72** across all five languages. **Real-document accuracy check, 2026-10-03:** the demo's one-sentence `hindi.txt` ("New Delhi is the capital of India") was joined by three real Hindi Wikipedia lead sections fetched live via the MediaWiki API (ताज महल/Taj Mahal, क्रिकेट/Cricket, हिमालय/Himalaya; 1.9–9.7 KB, CC BY-SA), indexed in the Docker demo and queried with 4 English prompts carrying zero shared vocabulary with the Devanagari text, so the lexical/BM25 pass cannot contribute and the ranking is pure `labse` vector similarity. Result: **top-1 precision 1/4 (25%), top-3 precision 3/4 (75%)** — the Taj Mahal query ranked its document #1, the India-capital and Himalaya queries ranked their documents #2 behind an unrelated document, and the cricket query never surfaced `cricket.txt` in the top 3 at all, losing to Spanish/German/French documents on an unrelated topic. Trimming the three long articles down to their first two sentences and re-querying did **not** improve the ranking (the short versions did no better than the full articles), which rules out 256-token truncation/mean-pool dilution as the cause. The likelier explanation: the existing "capital of France" smoke test (still passing, see item 5/Docker-demo note) shares the literal token "France" between the English query and the French passage, so it gets a lexical-pass assist that no English-vs-Devanagari pair can get — with that crutch removed, `labse`'s true cross-script semantic alignment for Hindi is visibly weaker than the single curated smoke-test query suggested. This sharpens the caveat above: usable for a curated single-document demo, **not yet reliable for arbitrary real-world Hindi content.**

**Follow-up, 2026-10-03 (same day):** the full sentence-transformers LaBSE pipeline (CLS pool -> trained `2_Dense` projection -> normalize, see above) was implemented and re-run against this exact same 4-query benchmark and the "capital of France" regression check (mean pooling was also tried in between, as an intermediate, less-grounded guess, before the `2_Dense` discovery). Result: **unchanged — 1/4 top-1 (25%), 3/4 top-3 (75%)**, with `cricket.txt` still never reaching the top 3 under any of the three approaches (raw CLS, mean pooling, trained CLS+dense projection), and the French regression query still correctly ranking `french.txt` first in all three. Three architecturally different, individually well-justified pooling/projection strategies landing on identical aggregate accuracy is itself a meaningful result: it rules out pooling-strategy choice as the cause and points to the ceiling being the frozen, int8-quantized embedding model's cross-lingual alignment quality on this specific small (8-document) corpus with several unrelated-language distractors, not an implementation bug — corroborated by the `TestMultilingualSmoke` same-language scores jumping to a properly spread 0.32–0.72 under the same trained-projection change, so the fix is working; this particular benchmark is just a harder, zero-shared-vocabulary task than same-language retrieval. Not started: a same-script control (e.g. romanized Hindi) to separate script effects from translation-quality effects, and a non-quantized (fp32) LaBSE export to rule out quantization noise as a contributor — both are backlog items, not blockers, given the benchmark corpus is only 8 documents and the result is now well-explained rather than mysterious. Select with `--model <id>` / `zenith.WithModel(id)`; `zenith models list|pull <id>` installs non-bundled ones (the registry names upstream files and does not pin checksums, so `pull` records the SHA-256 of what it fetched). An explicitly requested model that cannot load is an *error*, never a silent downgrade. **The index decides its model:** an index records `onnx:<id>` in its header, refuses to open with another (`ErrEmbedderMismatch`, with the exact way forward in the CLI), and the CLI follows the recorded model automatically when `--model` is not given — so changing the bundled default never strands an existing index. Measured, dense-only (no lexical signal, so the numbers isolate the model; MS MARCO = 2,000 dev queries over a 20k-doc slice, SciFact = full BEIR test split): all-MiniLM-L6-v2 nDCG@10 **0.946** / SciFact **0.652** (23 MB, 2m19s to embed 20k docs); bge-small-en-v1.5 **0.961** / **0.699** (34 MB, 4m30s; the query instruction prefix helps MS MARCO and slightly hurts SciFact); **gte-small 0.965 / 0.714** (34 MB, 3m52s). Full hybrid pipeline (lexical + dense + RRF): **out-of-domain SciFact** (300 queries, 5,183 docs): nDCG@10 lexical-only 0.689, +all-MiniLM-L6-v2 0.691, +bge-small 0.727, **+gte-small 0.738** (Recall@10 0.820 / 0.823 / 0.848 / **0.866**); **in-domain MS MARCO** (107,399 docs, 1,000 queries, exact vector scan): Recall@10 **0.962 for both** MiniLM and gte-small. So the previous default added almost nothing to BM25 on out-of-domain text, while gte-small adds +5 nDCG points; on in-domain text they tie. Cost of gte-small: ~1.7x embedding time (107k passages 21m41s vs 12m45s) and an 11 MB larger binary. *Caveat: the MS MARCO slice is in-domain for models trained on it and flatters them; SciFact is the more representative number for arbitrary user documents.*

### Monetization guardrails (risk #11) — rules applied while building

The open-core plan only works if the free engine stays trustworthy and the paid layer has somewhere to attach. These are constraints on every change, and where the code already leaves room:

1. **No telemetry, ever, by default.** A local-first search engine that phones home forfeits the funnel top. `zenith doctor --json` exists so a user *chooses* to attach diagnostics to a support request (versions, OS, paths, check outcomes — never index contents or queries); nothing is sent automatically. This is the paid-support on-ramp without a data-collection liability.
2. **No license-gated core features.** Filtering, crash recovery, install tooling, and the embedder-mismatch guard stay in the MIT library. What is left to charge for is operations, not correctness: hosted namespaces, backups/replicas, SLAs, and regional-language deployment support.
3. **Seams a hosted tier needs, already in place:** metadata attributes + pre-fusion filtering are the natural per-tenant isolation key (`Eq("tenant", id)`); the embedder identity header lets a hosted service swap or version models without silently corrupting customer indexes; `WithMemoryLimit` gives a per-tenant resource cap; versioned formats fail loudly instead of corrupting.
4. **Exit stays cheap.** Data lives in one directory; `zenith uninstall` keeps it by default and only deletes on explicit `--purge`. Lock-in through data hostage would poison an open-core funnel.
5. **What is still missing for monetization, deliberately not built yet (P2/P3 are gated on real users):** auth/quotas/metrics on the server, an export/backup command that a hosted tier could import, and tenant-aware limits. **Flag:** the repo had no `LICENSE` file although the README says MIT — without one, the open-core story is legally ambiguous to any adopter. A `LICENSE` file has been added to match the README; the copyright holder line is the maintainer's to confirm.
